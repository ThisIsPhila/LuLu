# Private per-record backup and restore review

**Date:** 26 October 2026  
**Result:** Local implementation and synthetic verification passed. Native-phone acceptance remains open.

## Contract reviewed

The existing private journal flow creates a password-encrypted file for one saved text record with all saved revisions, or one saved media original with its metadata. A restore requires the currently authenticated owner to match the file and both bound vaults. Imported content is re-encrypted under the current device key. No passkey, device key or account credential is exported.

Text preparation validates and snapshots one complete, unbranched history before asynchronous work. Media preparation validates the declared allowlisted MIME, byte length and digest. Restore preparation performs no record writes. Confirmation rechecks the expected stored state and uses one transaction to restore all text revisions plus the head, or the metadata and binary media rows. Identical stored history is a no-op; conflicting IDs and stale plans are rejected without overwrite. Confirmations are bound to the current session generation.

The file payload is a four-byte big-endian manifest length, UTF-8 JSON manifest and optional exact raw media bytes. The existing crypto primitive uses PBKDF2-SHA-256 (600,000 iterations), AES-256-GCM, fresh salt/IV and authenticated header fields. The maximum recovery payload is 64 MiB. Media is limited to 25 MiB. Backups contain saved records only; drafts, unsaved edits, other records, cloud data, passkeys and device keys are excluded.

No deployment, cloud mutation, commit or push occurred. The broader product goal remains active.
